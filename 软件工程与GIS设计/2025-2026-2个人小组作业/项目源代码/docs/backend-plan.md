# StarRunning 后端总体方案

## 1. 后端目标

这个项目的后端不需要做传统跑步 App 那种高频轨迹原始点存储和复杂计算，而是要服务“校园空间探索”玩法，重点解决四件事：

1. 管理玩法配置
2. 保存用户探索结果
3. 支撑探索结算与后续扩展玩法
4. 让前端逐步从本地静态规则迁移到云端配置

当前云函数已经承担了最小可用的数据写入职责，但还不是完整后端。下一阶段的总体方案应该是在不推翻现有云开发结构的前提下，把它整理成“配置域 + 用户进度域 + 会话域”三层。

## 2. 总体架构

建议继续使用微信云开发作为当前阶段后端基础，不额外引入独立服务器。

总体架构分为三层：

### 2.1 配置域

负责存放校园探索规则，给前端提供只读配置。

建议管理的数据：

- 校园运行时配置
- POI 配置
- 路线配置
- 成就配置
- 不可达区域配置
- 配置版本号

这一层的目标是替代前端长期直接依赖 `game-config.js` 的方式。

### 2.2 用户进度域

负责存放用户长期累计进度。

建议管理的数据：

- 用户基础资料
- 累计点亮网格
- 已发现 POI
- 已完成路线
- 已解锁成就
- 累计探索统计

这一层对应“长期状态”，不关心某一次探索的页面展示细节，只关心持久结果。

### 2.3 会话域

负责存放单次探索过程的结果和摘要。

建议管理的数据：

- 会话开始时间和结束时间
- 轨迹点数
- 本次距离
- 本次点亮网格数
- 本次发现 POI
- 本次完成路线
- 本次解锁成就

这一层主要服务：

- 探索结算页
- 历史记录
- 后续排行榜或周报能力

## 3. 数据模型建议

当前项目已经有 `userinfo`、`gridstatus`、`poi_records`、`track_sessions` 四个集合。建议在此基础上逐步演进，不要一次性重构数据库。

### 3.1 当前集合保留

- `userinfo`
  - 用户累计探索信息
- `gridstatus`
  - 用户点亮网格记录
- `poi_records`
  - 用户 POI 记录
- `track_sessions`
  - 单次探索会话摘要

### 3.2 建议新增配置集合

- `runtime_config`
  - 当前活动配置版本、地图开关、前端最小版本等
- `poi_config`
  - POI 坐标、名称、触发网格、解锁模式、题目绑定
- `route_config`
  - 路线目标网格、完成阈值、奖励
- `achievement_config`
  - 成就规则、文案、图标
- `unreachable_area_config`
  - 湖面、建筑内部、隔离绿化等不可达区域

### 3.3 可选新增结果集合

- `route_records`
  - 用户已完成路线记录
- `achievement_records`
  - 用户已解锁成就记录

这两个集合不是必须立刻加。现阶段也可以先把路线和成就写进 `track_sessions`，以及冗余到 `userinfo` 中。

## 4. 云函数拆分建议

当前项目把所有能力放在 `sdkpFunctions` 里。MVP 阶段这样可接受，但后续建议拆成更清晰的职责。

### 4.1 保留一个聚合入口的过渡方案

如果短期不想改前端调用方式，可以继续保留 `sdkpFunctions` 单入口，但内部拆模块：

- `handlers/profile.js`
- `handlers/grid.js`
- `handlers/poi.js`
- `handlers/session.js`
- `handlers/config.js`

这样前端接口不变，后端代码先降低复杂度。

### 4.2 中期拆分为独立云函数

建议拆成：

- `getRuntimeConfig`
  - 拉取当前生效配置
- `syncUserExploreProgress`
  - 批量同步网格、POI、汇总进度
- `syncExploreSession`
  - 写入单次探索结算
- `submitPoiQuiz`
  - 提交 `quiz` 型 POI 的答题结果
- `getUserExploreProfile`
  - 拉取用户累计进度

这样做的好处是：

- 前后端边界更清晰
- 每个函数更容易测试
- 后续权限和幂等控制更容易做

## 5. 前后端边界建议

后端应只负责“规则源”和“结果落库”，不要把空间计算强行迁回后端。

建议边界如下：

### 5.1 前端负责

- 实时定位采集
- 轨迹采样
- 网格命中判定
- POI 触发判定
- 路线与成就即时反馈
- 本地缓存和断点恢复

### 5.2 后端负责

- 配置分发
- 结果校验
- 进度落库
- 结算摘要存储
- 后续排行榜和统计聚合

原因很直接：

- 微信小程序的定位和地图交互必须在前端完成
- 实时探索反馈如果依赖后端会增加延迟
- 当前玩法更适合“前端实时判定 + 后端持久化”

## 6. 数据同步策略

建议采用“本地先行，云端异步确认”的同步策略，并明确三类同步对象：

### 6.1 高频同步

- 新点亮网格

策略：

- 前端本地先写
- 达到批量阈值后再同步

### 6.2 中频同步

- 新发现 POI
- 用户累计汇总

策略：

- 关键节点触发同步
- 每次探索结束强制补一次

### 6.3 低频同步

- 单次探索结算

策略：

- 结束探索时一次性写入 `track_sessions`

## 7. 规则迁移路线

当前规则主要在前端：

- `campus.js`
- `game-config.js`

建议分两步迁移，而不是一次性搬空。

### 第一步：前端静态配置为主，后端只读配置为辅

- 前端继续保留本地配置
- 后端提供同结构配置
- 前端优先用云端，失败回退本地

### 第二步：前端只保留地图基础数据，本地规则改为兜底

- `campus.js` 继续保留校园 GIS 基础数据
- `game-config.js` 只保留默认规则兜底
- 最终运行规则以云端配置为准

## 8. 安全与一致性要求

后端下一阶段至少要补以下约束：

1. 幂等写入
   - 同一 `grid_id`、`poi_id`、`session_id` 重复提交不能产生脏数据
2. 配置版本
   - 每次前端同步时带上配置版本，便于问题排查
3. 结果审计
   - `track_sessions` 应保留更新时间和用户标识
4. 基本校验
   - 校验字段类型、数组长度、关键 ID 是否为空

## 9. 后端实施顺序

建议按以下顺序推进：

### 第一阶段：整理现有云函数结构

- 不改前端调用协议
- 先把 `sdkpFunctions` 内部拆模块
- 补基础字段校验和幂等说明

### 第二阶段：增加运行时配置读取能力

- 新增配置集合
- 新增 `getRuntimeConfig`
- 前端支持云端配置加载和本地回退

### 第三阶段：支持 quiz 型 POI

- 新增题目配置
- 新增 `submitPoiQuiz`
- 解锁逻辑从“发现即完成”变为“发现后判题完成”

### 第四阶段：完善历史与统计能力

- 会话历史列表
- 基础排行榜
- 累计探索统计接口

## 10. 当前最合适的后端方向

如果和当前前端阶段配套，我建议后端近期优先做两件事：

1. 把 `sdkpFunctions` 内部模块化
2. 加入运行时配置读取接口

理由是：

- 这两件事不会打断当前 MVP
- 能直接为前端后续页面扩展和规则迁移服务
- 比立刻做排行榜、社交玩法更接近当前工程瓶颈
