## 1. 目标定义

前端当前的职责不是“记录跑步里程”，而是围绕微信小程序地图页面，完成“定位采集 -> 轨迹记录 -> 网格点亮 -> POI 发现 -> 路线/成就反馈 -> 本地缓存 -> 云端同步”的探索闭环。

下一阶段前端方案的目标是：

1. 保持现有 MVP 闭环可运行，不重写空间规则。
2. 把当前集中在首页的职责拆清楚，降低后续新增页面和玩法的改动成本。
3. 优先完成验收稳定化：真机定位、云端同步、页面数据展示和异常反馈一致性。
4. 为后续把规则配置迁移到云端保留接口，不把配置耦死在页面层。

## 2. 当前前端现状

当前前端已从单页地图应用扩展为 MVP 页面组：

- `miniprogram/pages/index/index` 仍是核心探索入口。
- `miniprogram/pages/session-result/index` 承担探索结算展示。
- `miniprogram/pages/history/index` 承担历史会话展示。
- `miniprogram/pages/poi-gallery/index` 承担 POI 图鉴展示。
- 地图页仍承担：
  - 定位权限与持续定位
  - 地图状态控制
  - 轨迹采样
  - 网格点亮
  - POI 判定
  - 路线/成就判定
  - 本地缓存恢复
  - 云端同步

这个结构已经能支撑 MVP 演示。后续风险主要在真机定位差异、云端同步失败恢复，以及独立 quiz/成就等扩展继续推高首页复杂度。

## 3. 前端总体架构建议

建议保持微信小程序原生技术栈不变，在现有项目上做“轻分层”，不做大规模框架迁移。

### 3.1 页面层

建议把前端页面逐步拆成以下结构：

- `pages/index/`
  - 地图探索主页面
  - 负责地图渲染、定位启动、探索流程控制
- `pages/session-result/`
  - 单次探索结算页
  - 展示本次距离、点亮网格、新发现 POI、新成就
- `pages/poi-quiz/`
  - `quiz` 类型 POI 的答题页
  - 管理题目展示、答题结果、解锁反馈
- `pages/achievement/`
  - 成就列表页
  - 展示已解锁/未解锁成就
- `pages/poi-handbook/`
  - POI 图鉴页
  - 展示已发现 POI、未发现 POI、说明文案

结算页、历史页和图鉴页已落地。独立 `poi-quiz` 和 `achievement` 仍是后续扩展。

### 3.2 组件层

建议把首页里复用性强、状态边界明确的 UI 先抽成组件：

- `components/explore-panel/`
  - 底部统计面板
- `components/gps-status-chip/`
  - GPS 状态胶囊
- `components/discover-toast/`
  - POI/成就即时反馈
- `components/session-summary-card/`
  - 结算摘要卡片

这样可以先减少首页 WXML/WXSS 的复杂度，再为后续页面复用。

### 3.3 业务模块层

建议把页面脚本中的业务逻辑按职责拆到 `miniprogram/services/` 和 `miniprogram/utils/` 下：

- `services/location-service.js`
  - 定位权限、定位启动、定位停止、弱信号判定
- `services/explore-session-service.js`
  - 探索开始、结束、会话摘要生成
- `services/grid-service.js`
  - 轨迹转网格、点亮去重、覆盖率统计
- `services/poi-service.js`
  - POI 发现、POI 解锁模式分发
- `services/achievement-service.js`
  - 路线完成与成就完成判定
- `services/sync-service.js`
  - 本地待同步数据整理、云端同步批处理

这样首页只保留“调度”和“视图绑定”，避免继续把所有流程堆在 `index.js`。

### 3.4 状态分层

建议把前端状态拆成三层：

- 页面即时状态
  - 地图中心点
  - 面板收起/展开
  - 当前定位文本
  - toast 展示
- 会话状态
  - 是否探索中
  - 当前轨迹点
  - 本次发现的 POI
  - 本次新增成就
- 持久状态
  - 已点亮网格
  - 累计成就
  - 已完成路线
  - 用户汇总信息

原则是：

- 页面即时状态只存在页面内
- 会话状态结束探索后可生成结算数据
- 持久状态统一由 `storage.js` 与云端同步逻辑维护

## 4. 首页改造方案

首页仍然是核心页面，但下一步不建议继续往里直接塞功能。建议按下面方式重构：

### 4.1 首页保留的核心职责

- 地图渲染
- 定位入口与开始/结束探索入口
- 实时探索态反馈
- 调用服务模块更新状态

### 4.2 首页移出的职责

- 结算数据展示移到结算页
- `quiz` 类 POI 的答题流程移到答题页
- 成就总览移到成就页
- POI 图鉴移到图鉴页

### 4.3 首页交互增强方向

- 开始探索前增加“准备态”提示
- 探索中增加更明确的“本次新增”反馈
- 结束探索后直接跳转结算页，而不是只 toast
- 对弱 GPS、越界、同步失败做统一的提示语和提示层级

## 5. 数据与接口约束

前端后续应遵守以下边界：

- `campus.js` 继续承载基础 GIS 静态数据
- `game-config.js` 仅作为本地兜底配置，不再长期承担最终规则源
- 页面层不得直接拼装云函数数据结构，统一走 `sync-service`
- `quiz`、路线、成就的判定逻辑应优先模块化，避免散落在页面事件里

为后续云端配置迁移做准备时，前端需要支持：

- 本地默认配置加载
- 云端配置加载
- 云端失败时自动回退本地配置

## 6. 下一阶段实施顺序

建议按以下顺序推进，而不是并行硬上：

### 第一阶段：整理现有首页

目标：

- 不改玩法规则
- 先把 `index.js` 降复杂度

动作：

1. 抽离定位、会话、网格、POI、成就、同步服务
2. 抽离底部探索面板组件
3. 整理页面状态字段，删除重复派生字段

交付结果：

- 首页仍保持现有功能
- 页面脚本明显变短
- 为新增页面扫清结构障碍

### 第二阶段：结算页稳定化

目标：

- 保持“结束探索”后的正式闭环稳定

动作：

1. 已完成 `pages/session-result/`
2. 已完成结束探索后生成会话摘要并跳转
3. 后续只需要在真机验收中确认本次距离、轨迹点、点亮网格数、发现 POI、新成就展示合理

交付结果：

- 用户结束探索后不再只看到 toast
- 答辩和演示链路完整

### 第三阶段：补 POI 答题流

目标：

- 实现 `quiz` 类型 POI 的正式流程

动作：

1. 新建 `pages/poi-quiz/`
2. 将 POI 发现拆成“发现”与“正式解锁”
3. 答题成功后再写入 POI 解锁记录

交付结果：

- `touch` / `quiz` 两种 POI 模式都能跑通

### 第四阶段：补成就页与图鉴页

目标：

- 从“即时反馈”走向“可回看内容”

动作：

1. 新建成就页
2. 新建 POI 图鉴页
3. 统一已解锁/未解锁展示逻辑

交付结果：

- 产品不再只有单次探索体验
- 可沉淀长期游玩目标

### 第五阶段：为云端配置迁移做前端适配

目标：

- 让规则源可以从本地文件过渡到后台配置

动作：

1. 定义配置拉取与回退机制
2. 约束前端只消费统一配置结构
3. 清理页面对本地规则文件的直接耦合

交付结果：

- 前端具备配置热更新基础
- 后续后台管理 POI/路线/成就时改动最小

## 7. 我建议的下一步

当前下一步最合适的是先做“MVP 验收稳定化”：

1. 微信开发者工具重新部署 `sdkpFunctions` 并确认云函数日志。
2. 真机跑通完整探索闭环，记录 GPS 精度和 POI 触发表现。
3. 保持 `npm test` 与 `npm run check:js` 作为每次上传前的固定检查。
4. 验收稳定后再进入独立 quiz 页面、成就中心、排行榜和社交玩法。

原因很直接：

- 核心页面已经齐备，继续扩展前先确认真机可跑。
- 课程/MVP 交付更需要稳定演示证据，而不是继续堆功能。
- 云端配置仍处于最小读取阶段，需要先验证本地兜底和线上环境行为。
